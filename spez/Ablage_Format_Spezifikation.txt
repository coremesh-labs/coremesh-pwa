Spezifikation: Ablageformat cm1 – Fassung 1 (2026-11-06, Ergänzung 1: Modulschlüssel)
=====================================================================================
Für den Bau der PWA (anderer Rechner) und des Exports. Hintergrund und Begründungen:
Ablage_Dateiformat_Konzept.txt; Abläufe: Ablage_Ablauf_Konzept.txt; File Explorer:
Ablage_Explorer_Modul_Konzept.txt. Was hier steht, ist verbindlich; „muss“ heißt: sonst Datei verwerfen.

1. Grundlagen
  Adresse der Ablage: Basis-URL mit „/“ am Ende; jede Datei liegt unter Basis + Pfad.
  Pfade:  i/<id>   veränderlich (Startdatei, Dataset-Index), i/modules (Modulliste)
          o/<hex>  Datendatei, unveränderlich, <hex> = SHA-256 der ganzen Datei, 64 Zeichen klein
          m/<hex>  Modulpaket, unveränderlich, ebenso
  IDs: 16 Zufallsbytes, base32 (RFC 4648) klein, ohne „=“ → 26 Zeichen, z. B. 7q2kx3…
  Zeitpunkte: RFC 3339 in UTC, z. B. "2026-11-06T14:03:00Z"; Tage: "2026-11-06".
  Texte: UTF-8. JSON: unbekannte Felder ignorieren (Erweiterungen kommen dazu, nichts wird umgedeutet).
  Leere Werte: der Export lässt leere Felder weg (kein null). Der Leser behandelt null wie ein
    fehlendes Feld (Text "", Liste [], Objekt nicht vorhanden) und bricht daran nicht ab.
  HTTP: GET. i/ ohne Zwischenspeicher holen (cache: "no-store"); o/, m/ dürfen dauerhaft
    zwischengespeichert werden. Die Ablage liefert CORS für die Adresse der PWA.
    Rückkanal: POST <adresse><id> (Adresse aus der Startdatei, z. B. …/r/), Inhalt = Nachricht
    (5.6). Antwort 201 angenommen, 200 schon da (Wiederholung), 400/413 abgewiesen (nicht
    wiederholen), sonst (auch 404/405: Worker ohne Rückkanal) bzw. ohne Netz später noch einmal. r/ ist von außen nicht lesbar.

2. Schlüssel und Schlüsselnamen
  Name                     Art                         Darstellung
  user:<uid>:<n>           Benutzerschlüssel, age      geheim "AGE-SECRET-KEY-1…", öffentlich "age1…"
  ds:<ablage-id>:<n>       Dataset-Schlüssel, age      ebenso
  srv-sig:<n>              Signatur des Servers, Ed25519  öffentlich: base64url ohne „=“ (32 Byte)
  srv-box:<n>              Rückkanal des Servers, age  öffentlich "age1…"
  mod:<bukr>.<modul>:<n>   Modulschlüssel, age         ebenso; je Modul eigener Schlüssel
  dev:<uid>:<n>            Signatur eines Geräts, Ed25519  geheim: Seed base64url (32 Byte) in der
                           Startdatei des Geräts; <n> = Fassung seines Benutzerschlüssels
  <uid> = zufällige ID des Teilnehmers, <ablage-id> = ID des Datasets, <n> = Fassung ab 1,
  <modul> = id im Manifest, <bukr> = Buchungskreis. Den Modulschlüssel hat nur, wer das Modul
  bekommt (Rolle); verliert jemand es, verschlüsselt der Export das Paket mit der nächsten
  Fassung neu (neuer Hash, neue Modulliste).
  Verschlüsselung: age v1 (https://age-encryption.org/v1), Binärform (nicht ASCII-Armor),
    genau ein Empfänger: der öffentliche Teil des Schlüssels aus „key“.
    Bibliotheken: Go filippo.io/age; Browser npm age-encryption (typage).
  Signatur: Ed25519 (RFC 8032), 64 Byte; im Browser WebCrypto "Ed25519" bzw. @noble/ed25519.

3. Aufbau einer Datei (Umschlag)
  Byte-Folge:
    magic      4 Byte   "cm1\n" (63 6d 31 0a)
    hlen       4 Byte   Länge des Kopfes, big-endian, höchstens 65536
    header     hlen     Kopf, JSON (UTF-8, ein Objekt)
    blen       8 Byte   Länge des Inhalts, big-endian
    body       blen     Inhalt
    signatur   64 Byte  nur wenn header.signed_by nicht leer: Ed25519 über alle Bytes davor
                        (magic bis Ende body)
  Danach darf nichts mehr kommen.
  Inhalt:
    header.key nicht leer → body = age-Datei; entschlüsselt = gepackte Daten
    header.key leer       → body = gepackte Daten (nur kind modules)
    gepackt: packing "gzip" (RFC 1952; Browser DecompressionStream("gzip")) bzw. "none".
  Kopffelder:
    format        "cm1"                                         muss
    kind          start | dataset | data | modules | module     muss
    path          eigener Pfad bei i/ ("i/7q2k…"), sonst ""     muss bei i/
    key           Schlüsselname oder ""                         muss
    content_type  Typ der entpackten Daten                      muss
    packing       gzip | none                                   muss
    name          ursprünglicher Dateiname (data), sonst ""
    size          Länge der entpackten Daten in Byte
    created       Zeitpunkt
    signed_by     "srv-sig:<n>" bei i/, sonst ""                muss bei i/
  Feste Paare kind → content_type:
    start    application/vnd.coremesh.start+json;v=1      key user:…   signiert
    dataset  application/vnd.coremesh.dataset+json;v=1    key ds:…     signiert
    modules  application/vnd.coremesh.modules+json;v=1    key ""       signiert
    module   application/vnd.coremesh.module+zip;v=1      key mod:…    nicht signiert (Hash in der Liste)
    data     beliebig                                     key ds:…     nicht signiert (Hash im Index)
  Parameter ;v=N im Content-Type: Fassung des Schemas. Unbekanntes N → Datei nicht verwenden,
    Hinweis „App aktualisieren“.

4. Prüfen beim Lesen (Reihenfolge, Fehlercodes)
  1. o/, m/: SHA-256 der ganzen Datei = Name im Pfad                         sonst E_HASH
  2. magic, Längen stimmen, nichts dahinter                                  sonst E_FORMAT
  3. Kopf: format "cm1", Pflichtfelder, kind passt zum Pfad und zur Erwartung sonst E_FORMAT
  4. i/: path = angefragter Pfad                                             sonst E_PATH
  5. i/: signed_by ist ein vertrauter Signaturschlüssel, Signatur gültig     sonst E_SIG
  6. key ist im Schlüsselbund (bzw. eigener Benutzerschlüssel)               sonst E_KEY
     (bei data: key = key des Elements im Index)
  7. Entschlüsseln (age)                                                     sonst E_DECRYPT
  8. Entpacken; Länge = size                                                 sonst E_FORMAT
  9. content_type = erwarteter Typ (bei data: wie im Index)                  sonst E_TYPE
  10. start, dataset: fassung nicht kleiner als die zuletzt angenommene       sonst E_OLD
  Bei Fehlern: Datei verwerfen, zuletzt gültige Fassung behalten, Fehlercode melden.

5. Inhalte (JSON)
  5.1 Startdatei
    {
      "fassung": 12, "erstellt": "2026-11-06T14:03:00Z",
      "teilnehmer": {"id": "<uid>", "name": "Gretchen", "pin_pflicht": false,
        "rollen": [{"rolle": "MIETER", "name": "Mieter", "bezug": {"art": "EINHEIT", "id": "…", "name": "Faustgasse 1, Whg. 16"}}]},
      "server": {
        "signatur": [{"key": "srv-sig:1", "public": "…", "gueltig_ab": "2026-11-06"},
                     {"key": "srv-sig:2", "public": "…", "gueltig_ab": "2027-01-01",
                      "signiert_von": "srv-sig:1", "signatur": "<base64url>"}],
        "rueckkanal": {"key": "srv-box:1", "public": "age1…", "adresse": "https://…/r/"}},
      "schluessel": [{"key": "ds:7q2k…:1", "secret": "AGE-SECRET-KEY-1…", "dataset": "7q2k…", "gueltig_ab": "2026-11-06"},
                     {"key": "mod:2000.explorer:1", "secret": "AGE-SECRET-KEY-1…", "modul": "explorer", "gueltig_ab": "2026-11-06"}],
      "datasets": [{"id": "7q2k…", "name": "Energie-Monitor Gretchen 2026-10",
        "sichtart": {"code": "VERBRAUCHSINFO", "name": "Energie-Monitor"},
        "sicht": {"id": "…", "name": "Energie-Monitor Faustgasse 1"},
        "berechtigt_ueber": "MIETER", "keys": ["ds:7q2k…:1"],
        "fassung": 3, "stand": 1, "geliefert": "2026-11-06T14:00:00Z",
        "neu_seit": "2026-11-01T00:00:00Z", "freigabe_bis": "2028-04-30", "modul": "explorer"}],
      "modules": ["explorer"],
      "hinweise": [],
      "geraet": {"nr": 2, "name": "Handy", "signatur": {"key": "dev:<uid>:7", "secret": "<base64url>"}}
    }
    modules: die Module, die der Teilnehmer bekommt (ihre Schlüssel stehen in schluessel). Ein
      Dataset, dessen modul nicht darin steht, kann die App nicht anzeigen (Hinweis zeigen).
    Signatur eines neuen Signaturschlüssels: Ed25519 mit „signiert_von“ über den UTF-8-Text
      "cm1-srv-sig\n" + key + "\n" + public + "\n" + gueltig_ab. Übernehmen nur, wenn gültig.
    Leere Listen datasets und schluessel = gesperrt: alles Lokale löschen.
    geraet: dieses Gerät (ein Teilnehmer kann mehrere haben, jedes mit eigenem Benutzerschlüssel
      und eigener Startdatei) und sein Signaturschlüssel für Nachrichten (5.6). Fehlt adresse
      bzw. geraet, gibt es keinen Rückkanal.
  5.2 Dataset-Index
    {
      "id": "7q2k…", "name": "Steuerunterlagen 2026", "fassung": 5, "stand": 2,
      "sichtart": {"code": "STEUERBUERO", "name": "Steuerbüro"},
      "zeitraum": {"von": "2026-01-01", "bis": "2026-12-31"},
      "geliefert": "2026-11-06T14:00:00Z",
      "gliederung": [{"ordner": "01 Eingangsrechnungen", "name": "Eingangsrechnungen"}],
      "elemente": [{"nr": 1, "ordner": "01 Eingangsrechnungen", "name": "2026-03-01_Stadtwerke.pdf",
        "titel": "Rechnung Strom März", "datum": "2026-03-01",
        "art": {"code": "ER", "name": "Eingangsrechnung"}, "partner": {"id": "…", "name": "Stadtwerke Auerbach"},
        "content_type": "application/pdf", "groesse": 183422, "key": "ds:7q2k…:1",
        "neu": false, "ref": "o/3f9a…"}],
      "modul": "explorer"
    }
    kennzeichen: fehlt oder {"code": "CANCELLED", "name": "storniert", "notiz": "…", "am": "2026-10-02"}.
    Ebenso fehlen leer: datum, art, partner, ersetzt_durch, zeitraum, gliederung, teile.
    ref "" = Element ohne Datei (nur im Verzeichnis). ersetzt_durch = nr eines Elements.
    teile: IDs weiterer Datasets (zusammengesetzte Sicht); deren Schlüssel stehen in der Startdatei.
  5.3 Modulliste
    {"fassung": 4, "erstellt": "…", "module": [
      {"id": "explorer", "name": "Dateien", "version": "1.0.0", "ref": "m/4b07…", "key": "mod:2000.explorer:1",
       "content_types": ["application/vnd.coremesh.dataset+json"], "sichtarten": ["*"], "rueckkanal": []},
      {"id": "vorgang", "name": "Vorgänge", "version": "0.1.0", "ref": "m/9c1e…", "key": "mod:2000.vorgang:3",
       "content_types": ["application/vnd.coremesh.process+json"], "sichtarten": ["VORGANG"],
       "rueckkanal": ["VORGANG_NOTIZ"]}]}
    Alle Module kommen über den Server, auch der File Explorer (mitgeliefert im Export). Die
    Liste ist signiert und unverschlüsselt; sie nennt alle aktiven Module, laden kann ein Modul
    nur, wer seinen Schlüssel hat. key: Schlüssel, mit dem m/… verschlüsselt ist (zur Anzeige
    „nicht freigegeben“, die Prüfung nimmt den key im Kopf der Datei).
  5.4 Modulpaket (zip)
    manifest.json: {id, name, version, einstieg: "<stem>.js", content_types, sichtarten,
      rueckkanal, api: 1} – muss zum Eintrag der Modulliste passen; dazu <stem>.js und
      <stem>_bg.wasm (wasm-bindgen, Target web). id: a–z, 0–9, - und _, höchstens 32 Zeichen.
      Der Export nimmt nur Pakete mit api ≤ der api der mitgelieferten App an.
  5.5 Objektdaten Vorgang (application/vnd.coremesh.process+json;v=1)
    {"id": "AF-2026-0001", "typ": {"code": "KLAERUNG", "name": "Klärung"}, "titel": "…",
     "status": {"code": "OPEN", "name": "offen"}, "eroeffnet": "2026-10-01", "abgeschlossen": null,
     "objekt": {"id": "…", "name": "Faustgasse 1"}, "einheit": {"id": "…", "name": "Whg. 16"},
     "beteiligte": [{"rolle": "MIETER", "name": "Gretchen"}],
     "ereignisse": [{"datum": "2026-10-01T09:00:00Z", "art": {"code": "NOTE", "name": "Notiz"}, "text": "…", "von": "Verwaltung"}],
     "anhaenge": [{"name": "Foto_Bad.jpg", "content_type": "image/jpeg", "ref": "o/77ab…"}]}
    Anhänge sind eigene Datendateien desselben Datasets und stehen auch im Index.

  5.6 Nachricht (Rückkanal), r/<id>
    Kopf: kind "message", path "r/<id>", key = srv-box:<n> (verschlüsselt für den Server),
    content_type "application/vnd.coremesh.message+json;v=1", signed_by = dev:<uid>:<n>.
    <id>: 16–64 Zeichen A–Z a–z 0–9 _ -, seit 2026.11.05-40 <ms>-<zufall>: Zeitstempel des Geräts
      in Millisekunden (Zahl, z. B. 1762509600000), dann 16 Byte zufällig base64url. Der Server
      verarbeitet in der Reihenfolge des Zeitstempels (ältere IDs ohne Zeitstempel: nach erstellt).
    {"id": "<id>", "art": "VORGANG_ANMERKUNG", "erstellt": "2026-11-07T08:35:09Z", "modul": "vorgang",
     "bezug": {"art": "VORGANG", "id": "AF-2026-0003", "dataset": "<ablage-id>"},
     "daten": {"text": "Es tropft wieder unter der Spüle."}}
    Die App sendet nur Arten aus dem Manifest des Moduls (rueckkanal) und nur mit Bezug auf ein
    Dataset dieses Moduls; ohne Netz bleibt die Nachricht im Ausgang und geht später. Der Server
    prüft Gerät (aktiv), Signatur, Modul, Art (Katalog) und Bezug (Teilnehmer sieht das Dataset)
    und verarbeitet sie genau einmal (id).
    Eingang des Servers (Queue): Er übernimmt jede Datei aus r/ mit Inhalt in seinen Eingang und
    löscht sie dann in der Ablage. Ohne gültige Signatur bzw. mit widerrufenem Schlüssel: „ungültig“,
    nur zur Kontrolle sichtbar. Verarbeitet wird nach dem Zeitstempel, je Objekt (bezug.art + id)
    eine eigene Warteschlange: scheitert eine Nachricht, warten die späteren desselben Objekts,
    die übrigen laufen weiter (Wiederholung mit wachsendem Abstand, dann „angehalten“).
    Nachrichten der App selbst (seit 2026.11.05-82): "modul": "app", nur Arten der Hülle
    (PUSH_ABO); der Server nimmt sie nur an, wenn die Art im Katalog „Von der App selbst“ ist,
    und prüft dann kein Modul-Manifest.

  5.6 Push-Benachrichtigungen (Web Push, seit 2026.11.05-82; RFC 8030/8291/8292)
    Startdatei: "server": {…, "push": {"vapid": "<P-256 unkomprimiert, base64url>"}} – fehlt es,
    bietet die Ablage kein Push an (z. B. ohne https-Adresse).
    Anmelden: Hat der Nutzer Benachrichtigungen erlaubt, holt die Hülle mit pushManager.subscribe
    (userVisibleOnly, applicationServerKey = vapid) die Push-Adresse und sendet sie einmal:
      {"art": "PUSH_ABO", "modul": "app", "daten": {"abo": {"endpoint": "https://…",
       "keys": {"p256dh": "…", "auth": "…"}}}}     (abo null = abmelden)
    Erneut nur, wenn sich Adresse oder Schlüssel ändern. Der Server speichert sie am Gerät.
    Für Fachmodule (Server): Das Objekt-JSON (Sichtart: Objektdaten = Object.Aktion) darf neben
      content_type, name, data … ein Feld "meldungen": [{"id", "titel", "text"}] liefern. Der
      Export merkt sich die Kennungen je Dataset; erscheint eine neue (nicht beim ersten Abbild),
      schickt er sie nach dem Veröffentlichen an alle aktiven Geräte mit Zugriff auf das Dataset.
      Je Sichtart abschaltbar (Push-Meldungen). Beispiel: Process.exportNotices (je Aushang).
    Inhalt (aes128gcm, für das Gerät verschlüsselt; der Push-Dienst sieht ihn nicht):
      {"titel": "Neuer Aushang: …", "text": "…", "modul": "<Modul der Sichtart>", "id": "<Kennung>"}
    Der Service Worker zeigt ihn als Benachrichtigung; Antippen öffnet ./#m=<modul>.
    Der Worker der Ablage ist für Push nicht beteiligt (nur für die Anmeldung über r/).

6. Einrichtungslink
  https://<Adresse der PWA>/#cm1:<base64url ohne „=“ von JSON>
  {"v": 1, "ablage": "https://…/", "start": "<start-id>", "name": "Gretchen",
   "key": {"name": "user:<uid>:1", "secret": "AGE-SECRET-KEY-1…"},
   "sig": {"key": "srv-sig:1", "public": "…"}}
  Die PWA übernimmt die Daten, entfernt den Teil hinter # aus der Adresse (history.replaceState)
  und holt die Startdatei. Als QR-Code im Einrichtungsbrief (Byte-Modus).

7. Prüfdateien (Testvektoren)
  In coremesh-erp unter pkg/cm1/testdata/ (Paket cm1, vom Export benutzt; neu erzeugen mit
  CM1_UPDATE=1 go test ./pkg/cm1/):
    keys.json     feste Prüfschlüssel (Benutzer, Dataset Fassung 1 und 2, Signatur 1 und 2)
    ablage/…      Dateien unter ihrem Pfad (i/…, o/…)
    expect.json   je Datei: {pfad, gueltig, fehler, inhalt_sha256, content_type}
  Fälle: data PDF none; data JSON gzip; Index; Startdatei; Startdatei mit neuem Signaturschlüssel;
    gesperrte Startdatei; Modulliste; falscher Hash (E_HASH); falsche Signatur (E_SIG); unter
    fremdem Pfad (E_PATH); unbekannter Schlüssel (E_KEY); abgeschnitten bzw. Bytes dahinter
    (E_FORMAT); falscher Content-Type (E_TYPE); ältere Fassung (E_OLD).
  Der Export prüft sich in seinen Tests gegen dieselben Dateien; die PWA ebenso.
  Dazu die Prüfablage (Konzept 7.11) für das Zusammenspiel.

7a. PIN in der App (export 0.17.0)
  Startdatei teilnehmer.pin = {"laenge": 6, "versuche": 5, "sperre_min": 5} (nur bei PIN-Pflicht;
  strengste Regel der Rollen). Die App legt dann einen eigenen age-Schlüssel an (Tresor im
  Browser-Speicher „cmT.tresor“: öffentlicher Schlüssel, geheimer Schlüssel mit der PIN
  verschlüsselt – age/scrypt 2^15 –, Zähler der Fehlversuche). Alle Einträge „cm1.*“, „mod.*“,
  „cmE.*“ (außer cm1.gemeldet) stehen danach nur als „cmT1:“ + base64url(age(gzip(Wert))) im
  Speicher. Abfrage bei jedem Öffnen und nach sperre_min Minuten im Hintergrund; nach
  „versuche“ Fehlversuchen löscht die App alles (neue Einladung nötig). Eine neue Einrichtung
  (Einladung, neuer Schlüssel) behält Tresor und PIN.

8. Änderungen am Format
  Neue Felder: jederzeit (ignorieren). Neue Schema-Fassung: ;v=N+1, der Export schreibt dann
  eine Zeit lang nicht ohne Not neu. Anderer Byte-Aufbau: "cm2".
